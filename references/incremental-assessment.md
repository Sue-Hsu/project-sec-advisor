# 基準與增量評估

在修正錯誤、新增功能或更新相依後，使用本方法決定本次應檢查的範圍。完整評估、增量評估與實際測試仍遵守主文件的授權及證據規則。

## 建立可比較的基準

1. 找出前次評估報告及其 `assessment_id`、受測來源快照、範圍、環境、工具／規則版本、測試 ID、實際證據、狀態及未涵蓋項目。來源快照優先使用 commit SHA；非 Git 專案可用具版本紀錄的發行物或內容雜湊。分支名稱與日期可輔助定位，但需有固定來源識別才能精確比較。
2. 將基準視為當時已知證據與涵蓋範圍的快照。它可以包含 `FAIL`、`INCONCLUSIVE` 或 `NOT_TESTED`；已規劃而未執行的項目只提供待測清單。舊狀態只屬於舊來源與舊環境，本次測試從 `NOT_TESTED` 起算。
3. 前次資料缺少固定來源、範圍或證據時，記錄可用部分及比較限制，將受影響項目納入較廣的盤點與測試計畫。保持前次報告原樣；本次產生新的 `assessment_id`。

## 追蹤變更與連動

1. 記錄本次來源快照與基準之間的 commit／PR 範圍；包含未提交變更時，記錄 base commit、dirty 狀態及變更檔案，將難以重現的部分列為限制。多儲存庫分別記錄來源；缺少差異工具時依可讀的變更紀錄與檔案逐項確認。
2. 從改動的程式碼、設定、依賴、建置及發行檔出發，檢查直接入口與呼叫者、被呼叫元件、共用授權／驗證／加密邏輯、資料流、信任邊界及下游功能。每個連動判斷保留來源位置或文件證據；無法確定的邊界列為待查並擴大相應測試。
3. 對應基準中的風險、既有發現與測試 ID，挑選本次回歸測試及新測試。對每個高風險影響面，記錄選入的測試、人工審查、延後項目及涵蓋缺口；「未改動」只有在依賴與資料流關係查清後，才能支持縮小範圍。

## 決定何時擴大複查

按專案風險、證據品質及發行節點規劃廣範圍複查。典型觸發包括基準不可比較、重大架構或信任邊界變動、新對外入口、共用身分／授權／加密控制變更、重大依賴或平台升級、難以追蹤的連動影響、嚴重發現、累積的未驗證缺口，以及重要發行前或專案約定的定期檢查。觸發原因與建議時點寫入報告；實際測試由已授權的執行流程完成。

本次評估若有固定來源快照、明確範圍與可追溯的實測證據，可作為後續評估的新基準；只完成規劃時可作參考紀錄，已測涵蓋維持原來的範圍與狀態。更新文件總覽的基準指標時，保留原報告與歷次連結。
