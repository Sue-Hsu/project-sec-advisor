# 評估方法

## 證據優先的盤點

從入口、執行環境、使用者與資料開始，依實際架構選擇檢查面。依序檢查專案／套件／鎖定檔、原始碼呼叫、設定、建置發行、部署文件；以「檔案路徑與行號／文件網址、觀察、推論、信心」記錄。套件存在時先記為相依證據，再由呼叫路徑或設定確認功能用途。將生成檔、範例、測試與生產路徑分開。

對每條資料流記錄來源、目的地、資料類別、傳輸方式、身分、授權決策及跨越的信任邊界。重要資產可為憑證、個資、付款資料、更新通道、軟體簽章、用戶檔案、管理 API 或下游服務。找出最可能被不受信任輸入、低權限角色或第三方控制的一端。

## 技術分流提示

以下是檢索提示；依已確認的架構選取相符項目。

| 架構 | 優先釐清的邊界與風險 |
|---|---|
| Web／API | Session、跨來源請求、輸入與輸出編碼、物件層授權、API rate limit、WebSocket／GraphQL 特性 |
| Windows 桌面／服務 | 本機檔案與 ACL、機密儲存、程序權限、IPC、更新來源與簽章、安裝與發行 |
| Mobile | 平台權限、裝置儲存、IPC／deep link、傳輸與憑證驗證、套件及發行 |
| CLI／背景工作 | 參數與環境輸入、檔案路徑、程序執行、排程身分、日誌與錯誤輸出 |
| SDK／函式庫 | 公開 API 契約、不受信任輸入、序列化、相依套件與下游使用情境 |

跨技術專案按實際元件合併；例如桌面客戶端連雲端 API，要評估客戶端及 API 交界，實際雲端帳號設定另記交接。

## 風險與驗證判定

- 已確認漏洞：具體受影響主體、資產、失效的信任邊界，以及可重現或足以直接證明失效的證據。標示觀察環境與限制。
- 疑似弱點：有可疑來源但缺少關鍵可利用條件；明列尚缺的事實。
- 架構風險：設計或暴露面引出合理威脅，尚非已確認漏洞。
- 未驗證要求：適用控制項與預期行為已知，但沒有測試證據。

用影響、可達性、暴露與現有控制排序。可達路徑尚未證實時，先將最佳實務偏離記為待驗證要求或架構風險。每個測試項目預設 `NOT_TESTED`；取得實測證據並依明確準則判定後，才改為 `PASS` 或 `FAIL`。`INCONCLUSIVE` 表示已測但證據不足，`NOT_APPLICABLE` 需附架構理由。

## 測試計畫

依風險與副作用排序，先規劃低風險、可離線的檢查，再規劃受控動態檢測。每步記錄授權目標、可用測試環境、資料保護、必要帳號、版本、命令或人工步驟、預期產物、判準及停止條件。執行依 Skill 主文件的授權界線判斷；掃描結果需人工複核，零發現僅記錄為該工具的觀察結果。

若檔案、網路或工具不可用，以現有證據界定結論，將受影響的控制項列入未驗證，並列出需要補查的來源。
